# Alerting on charts (technical concept)

Status: **draft (2026-11-02)**, after three grilling rounds. Decisions taken in them are marked
"(decided 2026-11-02)"; everything else is a proposal.

## 1. Context and goal

Alerting comes from the time before dashboards as code. A rule lives in an `alerts.yaml`, points at a SQL file of its
own and has nothing to do with the chart an engineer looks at when the alert fires. Nobody can tell from a dashboard
*when* an alert fires, it knows only red (no "tips"), one number per check (no "for each status code"), and after a
rule change its history still shows what the old rule said.

Goal:

- **An alert is defined on a chart**: "if this line goes over / under X, for each series of type Y, alert". The
  chart's query is the alert's query; the chart shows the threshold and when the alert was yellow or red.
- **Clear firing semantics**: yellow = over the threshold, not long enough yet ("tips"); red = over the threshold for
  N buckets in a row ("alerts"). Readable from the chart.
- **Backtest**: when would this rule have fired in the last 30 days, before and after a change.
- **Recompute on rule change**: the history always shows what the *current* rule says.
- **Fast feedback while writing a rule**: save, reload, see the strip.
- The few alerts that have no chart use the same rule.

Guiding principle (as in the other concepts): the least machinery that still behaves nicely.

## 2. Current state

In use: 5 rules for Ökokiste, about 16 for Solarwatt, a few for wetell. Most Solarwatt rules are `value_gt: 0` on
counts of matching log lines (panics, SIGSEGVs, failed River jobs, payment inconsistencies), with a dashboard URL
pasted into the message.

### 2.2 What is good and stays

- **Batch evaluation**: one query for a range, then judge each bucket in Go. Few queries, cheap, and the same logic
  can serve the live check, the backtest and the recompute (§3.4).
- **The running bucket is understood**: a monotonic aggregate (`count`) may alert on the running bucket, an
  `avg` must wait for the bucket to close (comment in `batch_evaluator.go`).
- **Changes only**: notifications and history rows on state changes, not on every check.
- **Virtual time** (`config.TimeProvider`) for deterministic tests.
- **Heartbeat of the alerter** (`alert_cron_monitor_*`): a dead-man switch for the alerting itself.
- **A failing notifier becomes a visible error state** instead of disappearing.

### 2.3 What is broken

1. Rules are separate from dashboards; SQL string tricks (`--BUCKET:`, `--HAVING--`, `--NOW--`) and magic column
   names (`time_ts`, `value`).
2. One value per check; more rows is an error, so "for each type Y" cannot be expressed.
3. No yellow, no duration ("for N buckets").
4. "No data" and 0 are the same: a broken or empty query looks like silence.
5. `check_every` (cron) and the bucket expression are two settings that must fit together by hand; this is why "when
   does it fire?" is hard to answer.
6. Batch evaluator: queries without a time bound (`TODO: coarse timestamp selection`), writes into the production
   history table, `ClearAll` truncates all of it, reads private fields of `AlertManager`, finds a bucket's row by
   linear search.
7. History is "what was evaluated back then"; after a rule change it is stale. The id contains the yaml path, so
   moving a file loses history.
8. The message is a fixed string: no value, no series, hand-pasted URL. Helvetikit is the only target, the client
   is always `default`.
9. **Most 15-minute and hourly rules look at an empty bucket** (found 2026-11-02 while reading, not reproduced;
   `dashica_alert_events` should show it): `@15minutes` is `*/15 * * * *` (gronx), so the check runs at :15:00 with
   `--BUCKET: toStartOfFifteenMinutes(--NOW--)` = the bucket that started this second. Events between :15:01 and
   :29:59 are never evaluated. The same holds for `daveEgressHighErrorRate` (`0 * * * *` with `toStartOfHour`).
   Affected: 9 Solarwatt rules (401, panics, health check, River worker / service, failed River jobs, non-info
   spike, ToU, egress). This is problem 5 in practice.
10. `failedRiverJobs` and `ssoRiverService` run the same SQL (two notifications for one event); the panic alert
    reads `full_logs`, the panic chart `mv_swtthome_logs` (problem 1 in practice).
11. Bugs found while reading (not reproduced):
   - `sendCronHeartBeat` defers `resp.Body.Close()` before checking `err`; when the GET fails, `resp` is nil →
     nil-pointer panic.
   - `PersistResultAndNotifyIfChanged` writes into `currentAlertStatus`, which only `LoadAlertStatusIntoMemory`
     creates; the batch path never calls it → nil-map panic unless something loaded it before.

## 3. Proposed solution

### 3.1 Overview

```
src/p_oekokiste/overview.go
  widget.NewTimeBar(q).X(15min).Y(Count).Fill(status).Alert(rule)
        │  hands the rule: base query, time bucket (X), value (Y), series (Fill)
        │  draws: threshold line + state strip, from its own /alert route
        ▼
lib/alerting  ── knows only Rule{query, time, value, series, condition}, never a widget
   Evaluate(rows, rule, now) → state per (series, bucket)          pure function, unit tested
   Scheduler      on each due time: 1 query over the last N+1 buckets → Evaluate → notify on change
   Recompute      on a new rule_hash: same query in daily chunks over 30 days → history
        │
        ▼
alerting.HistoryStore (interface)  ── ClickHouse implementation (alert_storage), other databases later
   dashica_alert_history   state changes per (alert, series, rule_hash)
   dashica_alert_notified  last notified state per (alert, series)
        │
        ▼
Notifier (Helvetikit)  ERROR / NORMAL / reminder, templated message + link to the chart
```

### 3.2 The rule in Go (decided 2026-11-02: on the chart, in Go; `alerts.yaml` goes away)

```go
errors5xx := sql.New(
	sql.From("mv_caddy_accesslog"),
	sql.Where("customer_tenant = 'oekokiste'"),
	sql.Where("status >= 500"),
)

widget.NewTimeBar(errors5xx).
	X(sql.Timestamp15Min()). // also the alert's bucket
	Y(sql.Count()).
	Fill(sql.Enum("status")).
	Alert(alerting.Above(200).For(2). // yellow at the 1st bucket over 200, red at the 2nd in a row
		EachSeries().                   // one state per status value; .Total() = sum over all series
		Name("http5xx").
		Message("Ökokiste: {series} 5xx at {value} (threshold {threshold})").
		Slack("#oekokiste").
		RemindEvery(4 * time.Hour))
```

- `alerting.Above(x)` / `alerting.Below(x)` create an `alerting.Rule` value; every method returns a changed copy
  (like the widget builders). `lib/alerting` does not import `lib/dashboard/widget`.
- `.Alert(rule)` on a time widget (`TimeBar`, `TimeLine`, `TimeHeatmap`) fills the rule's **roles** from the
  chart: query = the chart's base query (without the viewer's filters and time range), time = X. Value and series
  depend on the widget: `TimeBar` / `TimeLine` value = Y, series = Fill / Stroke / Z; `TimeHeatmap(Ordinal)`
  value = Fill, series = Y. `Fx` / `Fy` facets are part of the series (`host_name=a, level=error`). The widget
  only *carries* the rule and draws it.
- **Reusable dashboard functions take their rules as parameters** (decided 2026-11-02): there is no template concept,
  only Go functions with parameters (`templates.CaddyIngress(tenant, ...)`). Such a function receives the
  `alerting.Rule` values (name, threshold, Slack channel) from its caller and only decides which chart carries
  them; registered on two pages it gives two alerts, as the page path is part of the id.
- **Builder queries only** (decided 2026-11-02): `.Alert()` on a widget over `sql.FromFile` / `sql.FromString`
  is a startup error. Only three time charts read SQL files today (all on the Ökokiste overview), and each is about
  10 builder lines: time widgets do not group by Y, so Y can be any aggregate. New in `lib/dashboard/sql` for
  typing: `sql.CountIf(cond)` (kind count, may fire early) and `sql.Ratio(num, den)` (NULL when `den` is 0 →
  "no data"; replaces guards such as `all < 50 → -0.1`).
- **Name**: the stable key state, history and notifications hang on. The alert id is
  `<page path>#<name>`; a duplicate name on one page is a startup error.
- **`.Total()` / `.EachSeries()`** (decided 2026-11-02: each series its own state, chosen explicitly):
  `.Total()` is the default: the query run again without the series columns (not the sum of the series, which is
  wrong for `avg` and ratios); on a stacked bar of a count its threshold line sits on the top of the stack, on
  other charts it is a line of its own. `.EachSeries()` gives one state per series value, the notification names
  the series.
- **Every alert has a chart** (decided 2026-11-02: no `d.Alert` in v1): all current rules fit a chart (§5.3). An
  alert without a chart (`d.Alert(rule.Query(q)...)`, drawn by the overview with a generated chart) comes when a
  real case shows up.
- **Series limits** (decided 2026-11-02: configurable per rule): `.MaxSeries(n)` (default 50; above it the rule is
  in error "too many series") and `.ForgetAfter(d)` (default 7 days, see "Series that disappear" in §3.3).
- Collection: `dashboard.Builder` returns its rules next to its handlers when the page is registered
  (`RegisterDashboard` in `dashica.go`); the scheduler gets the list as a value, no registry.

### 3.3 When does it fire

Inputs per series: the values of the last `For + 1` buckets, the current time.

| State   | Condition                                                                                                     |
|---------|---------------------------------------------------------------------------------------------------------------|
| green   | the latest *closed* bucket is not over the threshold, and the running bucket is not over either               |
| yellow  | the latest bucket (closed or running) is over, but not yet `For` buckets in a row                              |
| red     | the last `For` buckets in a row are over; the running bucket counts only if it may fire early (below)         |
| no data | the value is not a count and the bucket has no row, or the value is NULL (`sql.Ratio`); grey, never notifies |
| error   | the query failed; shown on the chart and notified like red (as today)                                        |
| inactive| outside `.ActiveHours()`; grey, never notifies                                                               |

**A running bucket only raises the state** (decided 2026-11-02): it can turn green into yellow or red, never red
into green. Without this, every red count would turn green at minute 1 of each bucket (the new bucket is still
small). Green needs a closed bucket. During `ingest_delay` there are two open buckets (the previous one, not yet
closed, and the new one); both are "running" in this sense.

**Active hours** (decided 2026-11-02, replaces the time windows of cron): `.ActiveHours(7, 21)` (in
`alerting.timezone`, default `Europe/Berlin`) evaluates only inside the window; outside, the strip is "inactive".
Needed for wetell's app-auth rule (no logins at night). The Solarwatt daily job checks become `Bucket(24h)` counts
that fire early, i.e. as soon as the night's run exceeds the threshold; their resolve hysteresis (§3.6 rule 3) is
capped at 2 hours, not 2 buckets, so a daily rule does not stay red for two days.

**The running bucket** (decided 2026-11-02: if it is already over and nothing waits, alert immediately):

- A value that can only grow within its bucket (`sql.Count()`; later `Uniq`, `Max`) with `Above`: once the running
  bucket is over, it stays over, so it counts at once. `Above(0).For(1)` on a count of panics is red within one
  check of the first panic, not at the end of the bucket.
- Everything else (`avg`, ratios such as Ökokiste's order failure rate, and `Below` on counts) counts the running
  bucket only for yellow; red waits for the bucket to close. Otherwise it would fire on half a bucket.
- The builder knows the kind of Y (`kindCount` in `lib/dashboard/sql/fields.go`). For SQL files and expressions,
  `.Early()` declares "only grows".

**Late data**: a bucket counts as closed `alerting.ingest_delay` (default 2 min, to measure on production, §6)
after its end, so logs that arrive late are in.

**When it is checked**: rules that may fire early every minute; all others when a bucket has closed (plus
the ingest delay). `check_every` and the cron syntax go away; the bucket decides.

**Expensive early rules** (decided 2026-11-02): `.CheckEvery(5*time.Minute)` makes the running bucket's checks
rarer, for a rule that scans a lot (`full_logs`, `ILIKE`) every minute. It is not a cron: the check when a bucket
closes always runs, and each check reads the whole running bucket, so the "empty bucket" of §2.3, 9 cannot come
back. Each check's duration and rows read are shown in the overview, so the author sees when it is needed. Of the
current rules only the Solarwatt 401 rule still reads `full_logs` with `ILIKE`.

**Bucket** (decided 2026-11-02): the alert's bucket is a property of the alert. A fixed X
(`sql.Timestamp15Min()`) is taken over; with `sql.AutoBucket`, the rule must name `.Bucket(15*time.Minute)`, else
startup fails. The state strip is always drawn in the alert's bucket; the threshold line only when the chart's
current bucket equals the alert's, otherwise a hint "threshold per 15 min, zoom in to see it".

**Series that disappear**: a series known from the history (seen in the backtest window) and missing now is
evaluated with value 0 (counts) or "no data". So `Below(1).EachSeries()` per host fires when a host stops logging
entirely; a series not seen for `.ForgetAfter(d)` (default 7 days) is dropped.

### 3.4 One engine: batch evaluation for live, backtest and recompute (decided 2026-11-02: keep batch evaluation)

`Evaluate(rows, rule, now)` is the batch evaluator, cleaned up: rows are `(bucket, series, value)` sorted by
bucket, the output is a state per (series, bucket). Pure, no ClickHouse.

| Use       | Query range                                            | Writes                                    |
|-----------|--------------------------------------------------------|-------------------------------------------|
| Live      | the last `For + 1` buckets (`WHERE time >= …`)          | history changes, notifications on change |
| Recompute | 30 days, **in chunks of one day**, one after the other | history under the new `rule_hash`         |

- The query is the chart's query with the rule's bucket and a time bound, built by the SQL builder (no string
  replacement). The result is aggregated: 30 days × 96 buckets = 2,880 rows per series.
- **Cost** is the scan, the same as opening the dashboard on 30 days: cheap on the `mv_*` tables, seconds to
  minutes on `full_logs` with `LIKE '%panic%'` (estimate, to measure). So: recompute only on a new `rule_hash`,
  never when a chart is viewed; daily chunks with `max_execution_time` and a queue that runs one chunk at a time
  over all rules (a changed template recomputes many pages at once); live evaluation goes on meanwhile. Days not
  done yet show "recomputing" on the strip.
- **`rule_hash`** (decided 2026-11-02: the rule's own inputs, not the SQL text): hash of the table, the `WHERE`
  clauses, the definitions of value and series, the condition, `For`, the bucket and the active hours. A change in
  how dashica-src writes SQL therefore recomputes nothing. Message, Slack channel, reminder and `CheckEvery` are not
  in the hash (they do not change states).

### 3.5 History (decided 2026-11-02: stored in ClickHouse, rewritten on rule change; other databases later)

```sql
CREATE TABLE dashica_alert_history
(
    alert_id     LowCardinality(String),  -- '/p_oekokiste/overview#http5xx'
    series       String,                  -- '' for .Total()
    rule_hash    LowCardinality(String),  -- '' for event 'sent'
    event        Enum('state' = 1, 'sent' = 2, 'chunk_done' = 3),
    bucket       DateTime,                -- start of the bucket where the state began / of the recomputed day
    state        Enum('green' = 1, 'yellow' = 2, 'red' = 3, 'no_data' = 4, 'error' = 5, 'inactive' = 6),
    value        Float64,
    message      String,                  -- event 'sent': the text sent to Helvetikit
    evaluated_at DateTime64(3)            -- newer wins for the same (alert, series, hash, bucket)
) ENGINE = MergeTree
ORDER BY (alert_id, rule_hash, series, bucket)
TTL bucket + INTERVAL 90 DAY;

CREATE TABLE dashica_alert_notified
(
    alert_id      LowCardinality(String),
    series        String,
    state         Enum('green' = 1, 'red' = 3, 'error' = 5),
    since         DateTime,
    notified_at   DateTime
) ENGINE = ReplacingMergeTree(notified_at)
ORDER BY (alert_id, series);
```

- **History** holds state *changes* per (alert, series, rule_hash). Reads take the current hash; the state at the
  start of a range is the last change before it (`argMax`), so the "once a day" rows of today are not needed.
  Old hashes are never deleted by hand; they age out.
- **The same bucket can get several rows**: yellow then red in one running bucket, or a running bucket whose state
  changes when it closes. `evaluated_at` decides (`argMax(state, evaluated_at)`); a recompute that is run again
  after a crash writes the same rows again, which is harmless for the same reason.
- **`sent` rows** (decided 2026-11-02, replaces "no sent log"): every message sent to Helvetikit is a row with
  `rule_hash = ''`, so it outlives a rule change. The strip shows the current rule's states plus markers where a
  message really went out: "did we page at 10:15?" stays answerable after the rule changed.
- **`chunk_done` rows**: a recompute writes one per finished day and `rule_hash`; days without one show
  "recomputing" and are the ones the queue still has to run (after a restart too).
- **Notified** holds the last state that was sent, per (alert, series). It is what live evaluation compares with,
  so a deploy or a recompute never re-sends. Reads use `FINAL`.
- **Two containers at once** (decided 2026-11-02: possible during a deploy, no leader election): before sending,
  the scheduler reads `dashica_alert_notified` and writes its new state *first* (the claim), then sends. While old
  and new container overlap, both may still read the old state in the same second, so a duplicate is possible but
  is at most one message per change.
- **Orphans are resolved at startup** (decided 2026-11-02): a `dashica_alert_notified` row whose alert id has no
  rule any more (renamed, page moved, deleted) gets one `NORMAL` and is deleted. The migration's "`NORMAL` for the
  old ids" is the same mechanism, not a step of its own.
- Both tables sit behind `alerting.HistoryStore`, a small interface (append changes, read range, read/write
  notified). The ClickHouse implementation is the only one now; the SQL stays plain enough to port with the dialect
  layer of [other databases](2026-10-30-other-databases.md). The TTL is a detail of the ClickHouse implementation;
  another database gets a periodic `DELETE` of old buckets.
- `dashica_alert_events` stays readable until migration step 6, then is dropped.

### 3.6 Notifications (decided 2026-11-02: templated message + link, reminder while red, notify on resolve)

- **On change to red / error**: Helvetikit `ERROR`; **on change to green**: `NORMAL`. Yellow is shown on the chart,
  not sent (decided 2026-11-02: Helvetikit `WARNING` would post a second message when it turns red).
- **Reminder**: `.RemindEvery(d)` sends "still red since 10:15, now 47" while red. Helvetikit drops it today (see
  below); it needs a small Helvetikit change.
- **Template**: `{series}` (the red series with their values, at most 5, then "and 12 more"; for `.Total()` empty),
  `{value}` (the highest value), `{threshold}`, `{since}`, `{link}`. The link points at the chart on its
  page with a time range around the firing, built from a new flat config key `public_url` (decided 2026-11-02;
  env variable as for the other keys, documented in `dashica_config.example.yaml`); empty → no link.
- **Grouping instead of per-event alerts**: "exceptions for a customer" is `Count(exceptions).Above(0).EachSeries()`
  by customer. The first exception notifies at once (§3.3); further ones only raise the count while it stays red
  ("Exception X and 10 more"), another customer turning red goes into the collected thread reply (flood protection
  below); green, then the next exception notifies again. No per-event state, no watermark.
  Optionally `.Samples(q, 3)` adds the latest matching lines to the message (their text goes to Slack, as messages
  do today).
- Helvetikit id: `<alert id>` — one key per alert, not per series (flood protection below).

**Flood protection** (requirement 2026-11-02: never flood Helvetikit for one alert). Floods come from flapping
(red, green, red each bucket), many series at once, restarts / deploys / recomputes, and a failing ClickHouse that
breaks every rule at once. Each gets one rule:

1. **One incident per alert.** The alert is red when at least one series is red. Going red posts **one** top-level
   message: the red series (at most 5, then "and 12 more"), values, link. A series that turns red while the alert is
   already red does not post a new message.
2. **While red, only thread replies, collected.** New red series and the reminder go into **one** thread reply at
   most every `RemindEvery` (default 1 hour): "now also 504, 500; 502 still at 47". Needs the Helvetikit thread
   reply (open question 1); until it exists, nothing is sent while red — the chart shows it.
3. **Resolve with hysteresis.** `NORMAL` only after all series have been green for as many closed buckets as it took
   to turn red (`For`), at least 2. The strip still shows each bucket's real state; only the notification waits.
   A flapping alert stays one incident.
4. **A hard budget per alert:** at most 6 messages (top-level and replies) per hour; more are dropped, logged and
   counted on the chart ("4 notifications held back"). A safety net for bugs and rules nobody thought through.
5. **Only live evaluation notifies.** Recompute, restart and deploy compare with `dashica_alert_notified` and never
   send for the past; a changed rule sends at most the one change of its current state.
6. **Evaluation errors are pooled.** When more than 3 rules fail in the same check (ClickHouse unreachable), one
   message for Dashica as a whole ("ClickHouse unreachable, 17 rules cannot be evaluated", key
   `dashica/_evaluation`) instead of one per rule; a single failing rule is an incident of that rule as in 1–4.

Worst case per alert: one incident (one message, its edit on resolve) per flap cycle, cycles slowed down by 3, and
never more than 6 messages per hour.

**What Helvetikit does** (read 2026-11-02 in `helvetikit/app/src/Alerting/AlertingApp.php`,
`app/Http/Controllers/ApiPublicAlert.php`):

| Field / behaviour      | Helvetikit today                                                                                                                                                         | Consequence for Dashica                                                                                                    |
|------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|
| key                    | `group + "/" + id` (`AlertKey::id`)                                                                                                                                      | `group = dashica_<helvetikit_id_group>` stays, `id = <alert id>` (one key per alert, flood protection rule 1)             |
| `deduplication_mode`   | default `DEDUPLICATE`: an event whose state equals the key's last state is dropped                                                                                       | Dashica already sends changes only; a **reminder** (`ERROR` again) is dropped                                             |
| `alert_group`          | events of one group within 1 hour of the group's first event become **thread replies** under its Slack message (sliding window, a TODO in the code)                  | send `alert_group = <alert id>`; the thread replies of flood protection rule 2 need a field of their own (open question 1) |
| no `alert_group`       | the first `#word` of the message becomes the group (`AlertGroup::extractFromMessage`); an empty string groups everything with an empty group                           | always send a non-empty `alert_group`, so a `#` in a message never groups by accident                                      |
| `NORMAL`               | marks all open non-NORMAL events of the key as resolved and **updates their Slack messages in place** (strike-through, ✅)                                               | "notify on resolve" works as is                                                                                            |
| `WARNING`              | posts its own Slack message, like `ERROR`                                                                                                                               | sending yellow would post twice (yellow, then red) — a reason not to send it                                              |
| mute                   | `muteAlertOrGroupUntil` is an empty TODO                                                                                                                                 | silences do not exist anywhere yet                                                                                         |
| message                | Slack mrkdwn section, `ERROR - <message>`                                                                                                                                | links as `<url\|text>` work                                                                                                |

**The reminder needs a Helvetikit change.** Options: (a) a new field `reminder=1` that posts a thread reply under the
key's open event ("still red, now 47") — recommended, the thread keeps the history in one place; (b) the same, but
updating the original message in place (`updateMessage` exists in `PostToSlackAdapter`) — quieter, nobody is
pinged; (c) `deduplication_mode=NO` without a change in Helvetikit — posts a new top-level message each time, noisy.
The migration's "send `NORMAL` for every old id" (§5.1) works with Helvetikit as is.

### 3.7 On the chart

- Time widgets with a rule draw the threshold line (§3.3) and a **state strip** under the x axis: one row per
  series, colour per bucket, the tooltip says why ("over 200 for 2 buckets since 10:15").
- The widget serves `/alert` next to `/query`: history for the visible range and the current hash, plus the
  rule's summary (op, threshold, `For`, bucket, early or not) for the legend. The props that never change go into
  the widget's client fields (`dashica-gen`), as today for `AlertDetail`.
- `AlertOverview` becomes a list of all rules with their current state per series and a 30-day strip, read from
  `dashica_alert_history`; `AlertDetail` and `templates.Alerts` go away.

### 3.8 Developing a rule (decided 2026-11-02: reload only in v1)

- Locally `mise r watch` reloads after a Go change; the new `rule_hash` starts a recompute over
  `alerting.recompute_days` (2 locally, 30 in production), i.e. two chunk queries, and the strip shows the result
  in seconds. Same code path as production, no dev mode. Locally `helvetikit_alerting_url` is empty, so nothing is
  sent.
- Each chunk logs and shows (strip tooltip, debug panel) its duration and rows read, with the extrapolation to 30
  days; over a limit (say 60 s for 30 days) the rule is marked "expensive".
- **In-UI tuning (later)**: drag the threshold or change `For` on the chart, see the strip, and **write the value
  back into the Go source**, in local development only:
  - `alerting.Above(x)`, `.For(n)` etc. record their **call site** with `runtime.Caller(1)` (file and line), next to
    the value. That costs nothing and is the missing "where does it come from".
  - A dev-only endpoint (behind a new config key, never in production: it writes files) parses that file with
    `go/parser`, finds the call at that line and checks its argument is a **literal** (`200`, `2`). It replaces
    exactly the bytes of that literal (token offsets), so formatting and comments stay. `mise r watch` reloads,
    the new `rule_hash` recomputes 2 days, and the strip shows the result.
  - The argument is not a literal (a variable, a template parameter such as `templates.X(..., 200)`): the endpoint
    says where the value comes from and hands out a snippet to copy, like Explore's Go code. Following the value to
    the template's caller (`runtime.Callers`, the stack) is possible but more work; first only literals.
  - Needs file paths in the binary: a build without `-trimpath` (the case for `go run` / `mise r watch`).
  - Not codegen (thresholds in a generated or data file the UI edits): it would bring back a config file next to
    the code, the thing this concept removes.

### 3.9 Tests (proposal after the grilling: no SQL dumps any more)

- The SQL is visible on the chart the alert evaluates: if it is wrong, the chart is wrong. So the real-incident
  parquet fixtures, which mostly tested the `--BUCKET--` machinery, go away.
- `dashica-src`: unit tests of `Evaluate` on synthetic rows (`For`, running bucket, no data, series that appear and
  disappear, ingest delay); one e2e test of the scheduler with ClickHouse and virtual time.
- Per rule: the backtest on the chart before and after a change. "Freeze an incident" (store the rule's aggregated
  rows of a window plus the confirmed fire times as a Go test, series names pseudonymized via `lib/privacy`) is
  later, if regressions show up.

## 4. Alternatives considered

| Alternative                                      | Why not                                                                                                |
|--------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| Keep `alerts.yaml`, point at a widget id         | two places for one thing, ids are fragile, no type checks                                              |
| Standalone Go alert, chart references it         | query of rule and chart drift apart                                                                    |
| Rules edited in the UI and stored (Grafana)      | not reviewable as code, breaks dashboards as code                                                      |
| Two thresholds (warn / error) instead of `For`   | flaps on noisy counts; a duration says "it lasts", which is what pages someone (decided 2026-11-02)   |
| History computed on the fly when viewed          | a 30-day overview would rerun expensive queries for every viewer                                       |
| SQLite for history                               | the production container has no volume; new dependency; ClickHouse behind an interface is enough now |
| Per-event alerts with a watermark                | per-event state and late-log dedup; grouping by state (§3.6) covers the known case                    |
| Raw-event fixtures + query in CI                 | needs ClickHouse and log data (privacy); tests the SQL the chart already shows                        |
| Running bucket only for yellow                   | a count already over the threshold would wait up to one bucket; red should come at once               |

## 5. Risks and migration

### 5.1 Risks

| Risk                                                         | Mitigation                                                                                                   |
|--------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| Recompute of a changed template loads ClickHouse             | daily chunks, one at a time, `max_execution_time`, cost shown per rule                                       |
| Many series (e.g. per URL) explode state and notifications   | `.MaxSeries(n)` per rule (default 50); above it the rule is in error "too many series"                       |
| Flooding Helvetikit / Slack for one alert                    | one incident per alert, collected thread replies, resolve hysteresis, 6 messages per hour, pooled errors (§3.6) |
| Late logs make a closed bucket wrong                         | `ingest_delay`; measure the Vector → ClickHouse lag on production                                            |
| New alert ids: Helvetikit keeps the old ones open            | orphans resolved at startup (§3.5)                                                                            |
| Ingest stops (Vector down): counts are 0, `Above` rules green | a `Below(1)` rule per important table / host, as Ökokiste has today (decided 2026-11-02: written by the author, no built-in freshness check) |
| Moving a page changes the alert id, history starts empty     | recompute fills 30 days at once; documented                                                                  |
| A rule silently stops being checked                          | heartbeat (`alert_cron_monitor_*`) stays; each rule's last check time shown in the overview                 |
